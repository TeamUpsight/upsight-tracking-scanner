# Domain: detection and evidence

## Responsibility

Owns the normalized Evidence Bundle and deterministic conversion of captured facts into GA4, Meta, CMP/consent, product `view_item`, CMS, collection, confidence, reason, and overall statuses. The same rules must serve live finalization, tests, and replay.

## Primary files

- `src/types.ts` — status unions, `TrackingRequestEvidence`, `EvidenceBundle`, `StorefrontAudit`, feedback contracts.
- `src/scanner/evidence/evidence-collector.ts` — bounded capture, installation and request normalization.
- `src/scanner/tracking/ga4.ts` and `meta.ts` — central vendor parsers and normalized evidence conversion.
- `src/scanner/consent/detect-cmp.ts` — multi-signal provider detection and confidence.
- `src/scanner/consent/consent-state.ts` — verified rejection/acceptance transitions.
- `src/scanner/server-side/classify-collection.ts` — actual collection scope and strict duplicate classification.
- `src/scanner/resolver/status-resolver.ts` — consent, product payload, and overall status semantics.
- `src/scanner/quality/consistency.ts` — correction of impossible cross-module combinations.
- `src/scanner/quality/replay.ts` — canonical evidence-to-result composition.
- `src/scanner.ts` — compatibility facade; keep old public names backed by shared V2 logic.

## Evidence and decision flow

Capture inputs are reduced to a versioned bundle with `page`, `network`, `consent`, `product`, `server_side`, and `runtime` sections. Consent V2 enriches the consent facts in that bundle before it is completed; it must not overwrite replayed decision fields afterward. Vendor parsers recognize qualifying requests or data-layer events; the collector stores bounded normalized fields. CMP and collection classifiers interpret their fact sets. Status resolvers choose conservative findings. Replay composes those results, runs consistency, writes the canonical `decision_summary`, and returns the fields used by live finalization, debug exports, UI, and offline comparison.

Key distinctions must remain explicit: installation versus actual collection; generic Google collection versus GA4; third-party versus first/same-origin collection; CMP presence versus a verified consent transition; PDP discovery versus a valid URL-matched product event.

LN-01 Tracking truth: a dataLayer `view_item` is retained as product-event implementation evidence, never proof of GA4 installation, collection, or a collected product event. A GA4 product pass requires a network `view_item` collection with usable product data associated with the verified PDP. Complete negative PDP observations cannot override unresolved Tracking/Consent gating merely by being repeated; a definitive `GA4_NO_VIEW_ITEM` under that gate requires a PDP-local GA4 collection and complete request observation. Sold-out availability is independent of PDP validity, so a semantically valid sold-out PDP receives the normal tracking observation.

LN-02 PDP association: scanner phase records operational chronology only. Browser Page identity plus its navigation epoch is primary request provenance; the vendor-declared `page_url` is explicit request provenance and remains separate from the sanitized browser-observed URL. Main-frame document and History API route transitions advance the epoch. A request without Page/epoch provenance may associate through a matching explicit vendor page URL, including Service Worker and historical evidence. Missing identity and missing vendor URL never imply the current PDP. Canonical replay applies these rules under rule pack `2026.09.26.2`.

LN-03 GA4 wire and privacy: compact `prN` values are split on literal wire-level `~` before token decoding; up to 20 products are considered in numeric order, with the first usable item supplying canonical fields. Up to 20 logical events from one GA4 batch request retain the same browser provenance while `network.total_requests` counts the physical request. A custom path qualifies as GA4 when `v=2`, `tid` is a `G-` measurement ID, and `en` exists; this does not establish Google Tag Gateway or server-side collection. GA4 `cid`/`sid` and Meta `fbp`/`fbc` become bounded, opaque tokens scoped to one audit. Replay converts legacy raw fields to replay-local tokens without mutating stored input. Persisted vendor `page_url` retains only protocol, host, and path. Rule pack `2026.09.26.3` applies these changes without changing Server-side classification policy.

LN-04 Server-side collection: new request evidence classifies collector relationships from the physical request URL and observed page URL. `same_origin` requires equal scheme, normalized host, and effective port. `first_party` means a different origin with the same PSL registrable domain; `third_party` means different registrable domains. Missing or invalid page origin and domains without a reliable registrable domain are `unclassifiable`. Committed storefront URL is a bounded fallback only after valid page observation; unassociated Service Worker requests remain unclassifiable. Historical evidence retains its stored `collector` value during replay. The provider-neutral detector reads bounded query/body structure and persists only allowlisted semantic groups and codes, never raw values. Paths are supporting context, not proof. Strong generic candidates require at least four recognized fields across three groups; medium candidates require at least three across two groups and only corroborate within the same origin/path family. Functional storefront APIs and technical telemetry are negative evidence. Generic first-party evidence can reach `first_party_collection_detected` at most; an ambiguous medium or unclassifiable strong candidate remains inconclusive. Candidate retention is capped at 50 normal or 100 diagnostic with explicit truncation. Rule pack `2026.09.26.4` introduced these qualifications.

LN-05 Server-side decisions: rule pack `2026.09.26.5` caps qualified same-origin or first-party measurement at `first_party_collection_detected`. This is high confidence that the browser sent a measurement request to that collector, not a claim of downstream forwarding, enrichment, deduplication, sGTM, or Google Tag Gateway. Request repetition, collector cookie names, historical cookie persistence, and strict duplicate correlation cannot raise or lower that status. Strict duplicates remain bounded diagnostic evidence; first-party plus third-party collection reports `mixed` without implying misconfiguration. New Server work has no cookie-persistence reload or wait. A Server negative requires passive classification and completed BrowserContext request capture; DataLayer and Performance Timing are Tracking supplements. Candidate or retained-request truncation blocks unsupported negatives, while an observed first-party positive survives incomplete or truncated observation. Response cookie names are captured only for qualified collection responses with an observed same-origin or first-party relationship. Existing cookie fields remain readable for historical bundles but no longer affect classification.

LN-06 launch closure uses rule pack `2026.09.26.6`. A definitive selected-module failure outranks an unrelated selected-module inconclusive result when access succeeded; an access error still makes the aggregate inconclusive. Tracking negatives require an untruncated relevant-request channel, while collection positives survive truncation. A previously verified PDP with a valid network `view_item` survives a later candidate navigation failure. Finalization rebuilds reason codes and decision summaries from corrected fields, and unselected modules have `not_tested` decision metadata. `src/scanner/quality/ln06-launch-regression.test.ts` guards these boundaries and the shared live/replay finalizer.

Diagnostic Consent control evidence is bounded and non-decisional. When a deterministic provider has visible Consent UI but exact semantic discovery yields no candidates, Playwright accessibility roles may expose at most 20 normalized names from locally corroborated Consent scopes, prioritized by visible/enabled/direct actionability. These names never create actions. A diagnostic screenshot is associated only when captured at the same observation boundary; its signed delta is `screenshot_time - observation_time`, so an earlier image remains explicitly negative rather than appearing contemporaneous.

### Usercentrics action boundary (WP17A)

Usercentrics identity uses exact provider loaders, `UC_UI`, or a known root; German consent labels alone are never provider identity. Lifecycle observations (`UC_UI_INITIALIZED`, `UC_UI_VIEW_CHANGED`, `CMP_SHOWN`) establish readiness or visibility, never a consent decision. The legacy executable path requires an exact, visible, enabled control inside the open `aside#usercentrics-cmp-ui` shadow root. The separately qualified Browser UI path is described below. Generic main-frame observations remain non-executable.

### Usercentrics Web CMP v2 semantic channel (WP17B)

Only the `app.usercentrics.eu/browser-ui/.../loader.js` plus initialized `UC_UI` path can use the v2 semantic reader. The v3 `web.cmp.usercentrics.eu/ui/loader.js` path remains observation-only for this package, including when both loaders are present. The bridge calls `UC_UI.getServicesBaseInfo()` and returns bounded essential and non-essential counts, read status, and a boolean indicating that each non-essential service's latest history entry is explicit and agrees with its current status. A fresh all-false default without that history is `unanswered`, not rejected. Essential services may remain granted. The bridge never returns service identities, raw histories, consent strings, or event payloads.

The pre-navigation listener retains only the latest 20 built-in `UC_UI_CMP_EVENT` names and observation times. Post-activation `DENY_ALL` can corroborate a freshly read rejected runtime; `ACCEPT_ALL` contradicts requested Reject. `SAVE`, `CMP_SHOWN`, initialization, and view changes are not Reject proof. Runtime projections share `usercentrics_runtime`; the built-in semantic event has separate `usercentrics_event` provenance. A post-action TCF `useractioncomplete` may independently corroborate when its listener reports a new event after activation. Pre-action capability requires a readable initialized v2 service channel with at least one non-essential service and the installed event listener, even if current consent is unanswered. Persistence reload is attempted only after verified Reject and requires the v2 provider state to remain rejected after same-context initialization; storage is supporting only. The semantic reader, evidence groups, TCF corroboration, and persistence behavior are independent of the Browser UI target topology.

### Main-frame ownership census (WP17C.7)

Audit 552 is compiled, clean, and certifiable observation evidence for the current Congstar v2 `UC_UI` runtime. It establishes provider identity, a visible banner, and a readable verification channel. Its screenshot shows three German controls, but the saved audit did not retain their DOM owner. The screenshot and `FIRST_LAYER` lifecycle alone cannot establish DOM ownership. The subsequent read-only manual DOM capture identified the exact open-shadow Browser UI owner described below; it does not retroactively change Audit 552/553 records.

Diagnostic Consent captures now census only main-frame surfaces already classified as visible, cookie/privacy semantic, consent-intent, and strongly presented by the bounded browser-facts detector. The census retains capped counts, role/modal facts, exact semantic action presence, direct actionable owner counts, and a fixed marker-family vocabulary. It never passes generic controls to `invoke_control`. A visible provider banner without a qualifying generic surface is reported as `main_frame_unowned` with `main_frame_consent_surface_count=0`; this is a coverage gap, not ownership evidence. Two qualifying surfaces or duplicate direct Reject controls are ambiguous. A descendant's text does not become a direct target when its actionable ancestor has a different accessible name.

The generic census still treats a full `usercentrics-` identifier prefix or `data-usercentrics` attribute name within a confirmed main-frame surface only as `provider_prefix_candidate_present`. This is a diagnostic hint, not main-frame ownership proof. Generic `uc`, `cookie`, `consent`, `privacy`, `cmp`, `banner`, and `modal` tokens cannot establish Usercentrics ownership. No executable main-frame topology has been certified; `main_frame_provider_owned` remains reserved.

The diagnostic projection also retains the v2 reader's existing normalized pre-choice decision and explicit-decision boolean (or `unknown` when unreadable). This does not change v2 semantics, action eligibility, provenance requirements, or provider API interaction policy.

### Usercentrics Browser UI open-shadow topology (WP17C.8)

A read-only manual capture of the current Congstar first layer found one `div#usercentrics-root` with an open shadow tree and a visible `div#uc-center-container[role="dialog"][aria-modal="true"][data-testid="uc-tcf-first-layer"]` inside it. The legacy `aside#usercentrics-cmp-ui` was absent. The Browser UI host itself can have no visible box; visible owned descendants determine whether its UI is displayed. The diagnostic census reports this exact qualified structure as `open_shadow_browser_ui`, separately from `open_shadow_standard` and the non-executable main-frame census.

Browser UI discovery requires a selected high-confidence or deterministic Usercentrics provider, `v2_uc_ui`, exactly one Browser UI root, its open shadow tree, and exactly one visible qualified first-layer dialog. A directly actionable, visible, enabled button must have composed shadow ownership back to that root, belong to the qualified first layer, and agree on both provider-specific test ID and exact normalized accessible label: `uc-deny-all-button` with `Alles ablehnen` (Reject), `uc-accept-all-button` with `Alles akzeptieren` (Accept), or `uc-customize-button` with `Einstellungen verwalten` (Preferences). Existing approved English labels can agree with the respective test IDs. Conflicting identities, duplicate roots/layers/buttons, missing shadow, hidden or disabled controls, and controls outside the first layer do not yield a target. Invocation re-discovers the target and checks the same contract immediately before any future click. No provider API fallback or generic-dialog ownership bridge is used. Deterministic fixture coverage establishes the new discovery path; no live Reject has been performed or verified.

WP17C.1 keeps unexpected common Consent observation exceptions inconclusive and marks the failing logical stage and operation in the shared or fresh audit trace. The markers preserve the original exception for the existing error-family classifier and expose no message, stack, DOM, selector, or provider payload. A throwing or malformed `UC_UI` service API remains a bounded `read_status` failure with unavailable semantic action capability; it does not become a negative CMP finding. Audit 546 passed storefront and EU transport checks but failed both observation paths before provider detection, so its current provider/runtime and root cause remain unestablished.

WP17C.2 marks the internal browser-facts substage inside the core evaluation and the separate Usercentrics DOM/runtime evaluation. A failed evaluation surfaces a fixed substage and error family in the existing technical observation failure; it never returns empty provider facts or a CMP-negative result. Browser exception text and stacks are discarded at this boundary. Playwright context destruction, navigation interruption, and page closure are classified separately from in-page runtime exceptions. Optional provider reads are not newly suppressed by this diagnostic change.

WP17C.3 narrows generic main-DOM failures to fixed enumeration, text, control, visibility, style, and classification substages. Individual surface text and control accessible-name getters may fail without aborting otherwise valid browser facts: the capture tries only existing approved DOM sources, retains bounded diagnostic error counts, and leaves unreadable visible surfaces as missing evidence. The generic detector returns inconclusive when unreadable visible text would otherwise produce a negative finding. DOM enumeration, style/layout reads, browser context loss, and serialization remain technical failures. No provider-specific action or verification semantics change.

### US privacy semantics (WP12A)

US privacy rights are a parallel descriptive model under `evidence.consent.us_privacy`; they never extend `ConsentActionType`, `AvailableAction`, Reject planning, or Reject verification. A bounded exact-label classifier can record `opt_out`, `limit`, `opt_in`, or `manage` choices over sale, sharing, targeted advertising, profiling, and sensitive-data-use rights only from a confirmed privacy/CMP surface or confirmed provider control. Generic acknowledgements and arbitrary privacy-policy text do not become actions or rights. In USA Cookiebot observations, a standard selector is not sufficient to establish a cookie action when its accessible name instead identifies a US privacy choice; EU/UK selector behavior is unchanged.

The projection passively reads `navigator.globalPrivacyControl` as present, absent, or unavailable and separately records a bounded on-page GPC acknowledgement. It does not set GPC, send `Sec-GPC`, exercise a right, or claim that GPC was honored. Existing sanitized GPP ping facts remain framework-owned; applicable section IDs are copied as framework-declared context with `state_verified: null`, never as proof of physical state or a legal-compliance verdict. Canonical replay preserves this evidence without deriving `consent_status` from it. The existing status resolver already limits prior-consent violations to EU/UK, so USA pre-choice tracking remains outside that verdict.

### GPP structure (WP13B)

The GPP observer keeps CMP-supported section IDs, payload-present section IDs, and CMP-declared applicable section IDs as separate bounded facts. The GPP `[-1]` applicable-sections sentinel is preserved as the CMP declaration that no section applies to the current transaction; it is not a legal applicability conclusion. Known section IDs receive technical labels from a small registry; unknown IDs remain observable without invalidating the rest of the observation. These labels identify framework representation only and do not infer visitor geography or governing law.

The browser bridge reads the API's parsed-section keys and persists only bounded API prefixes and whether parsed data was exposed. It never copies parsed field values or `gppString`. An applicable ID absent from `sectionList` is structurally inconsistent; missing parsed representation is inconclusive/unavailable. A signal that is not ready keeps applicable section state incomplete even when parsed data exists. Parsed field values are intentionally uninterpreted: WP13B does not normalize GPP choices into WP12A rights because this structural observer has not established a safe, section-specific field mapping. No compliance verdict is derived.

Regression entry points: `us-privacy.test.ts`, `cookiebot-adapter.test.ts`, `v2-session.production.test.ts` (WP12A cases), and the USA status/replay cases in `scanner-core.test.ts`. Debug packages expose the same bounded projection in `us-privacy.json` and `consent-summary.json`.

### Controlled GPC comparison (WP12B)

The optional USA diagnostic `GPC_EXPERIMENT_ENABLED` path uses two fresh, service-worker-blocked contexts. The canonical scanner keeps its configured Browserless route (normally `/stealth`). Both experimental Browserless sessions now use the standard route with the same proxy-session URL, locale, and ordinary launch options; only their Chromium GPC feature flag differs. OFF requests disabled GPC force/test features; ON requests the GPC force feature. Neither Browserless arm adds a synthetic DOM property, `Sec-GPC` extra header, or Playwright route override. If the canonical connection has no reusable Browserless configuration (for example, a BrowserQL handoff), the experiment is inconclusive rather than reverting to an in-session synthetic profile. Local fixture arms retain their synthetic HTTP/DOM profile because the local Chromium build cannot reproduce the hosted GPC behavior. CDP sent-header events still record bounded first-party and top-level `Sec-GPC` states, and the observed DOM value must match; configuration alone never validates transport. If standard Browserless still sends `Sec-GPC: 1` in OFF, the result is `transport_invalid` with `BROWSER_PROVIDER_GPC_OFF_UNAVAILABLE`, not a comparison verdict or scanner/legal failure. The per-arm context stage permits up to 12 seconds for the added Browserless connection, within the unchanged arm and global budgets. Session comparisons require matching browser versions, standard route, locale/timezone, and independently verified USA egress fingerprints. Separate sessions may yield different egress identities, in which case the result remains `identity_unmatched`. The pair reuses passive Consent UI, US privacy, GPP, Access, and normalized Consent measurement observers; it never clicks, scans Product/Server-side, or contributes to replay. Invalid transport, identity, access, or budget yields an inconclusive technical result. No outcome asserts legal compliance or that GPC was honored. Audit 514 proved that Browserless `/stealth` still sent `Sec-GPC: 1` in the OFF session despite the prior launch flag (22 of 22 bounded first-party requests); the standard-route attempt still requires one authorized live sent-header validation. If it also cannot establish OFF, retain passive GPC observation, leave this experiment disabled by default, and close synthetic GPC hardening without more header/browser workarounds.

WP12B.1 budgets the sequential arms separately: each receives 24–30 seconds only when the audit's remaining optional allowance can cover both arms plus a 2-second experiment margin, in addition to the runtime budget's finalization reserve. Context, egress, setup, navigation, passive observation, and transport verification each have bounded stage caps. Diagnostic timing retains completed stages and either arm's completed evidence even if its peer times out; stage-specific and total-deadline reason codes remain non-canonical. Insufficient remaining allowance skips the pair as inconclusive without borrowing the global audit deadline.

### Consent V2 pre-choice provenance (WP08)

`tracking-consistency.ts` normalizes Consent request facts and owns reconciliation. Shared requests use only `consent_initial_load`, `product_discovery`, and `product_pdp_load`; fresh requests use that session's choice timestamp. Each normalized record retains context, phase, timestamp, timing, evidence type, signal kind, and measurement facts. The shared GA4 parser supplies wire classification, including each bounded batch line. Event presence alone never establishes full measurement. The GCM observer can add a denied analytics-storage fact from commands in the same context at or before the request; later commands and shared/fresh cross-context commands cannot classify it. Opaque `gcd` and GPP encodings are not decoded.

Within a source, positive full and limited facts are monotonic; both yield `unknown` with `contradiction: true`. Across contexts, agreeing positive states retain that state; disagreement or an unknown measurement window yields `unknown`. An empty/script-only window supplies no contradictory positive fact. No evidence is `false` (not observed), not a compliance finding. A truncated window without positive evidence is unknown.

`runtime_metrics.consent_v2.measurement` stores the bounded source records, state, contradiction/truncation flags, and counters. Compatibility, replay, and `consent-summary.json` consume this same provenance. `tracking_requests_observed` counts supported requests captured in the scoped source, including overflow; `tracking_requests_retained` counts the bounded records. `tracking_signals_classified` and the pre-choice event/conversion/script counters count those retained records, so they are lower bounds when truncated. Event hits include recognized GA4 collections without an event name; script loads are always distinct. Full/limited counters count pre-choice records containing each positive fact (a conflicting record can contribute to both). Unknown counts count records with unknown classification. GCM network/command counts count the owning observer's retained observations, not tracking events. Source counts add without deduplicating separate browser contexts.

Consent buffers retain at most 100 requests per context and preserve examples of both explicit positive classes on overflow. This Consent-only buffer also preserves provenance when the shared tracking bundle reaches its independent cap; it does not change tracking capture, product budgets, or browser timing. Production remains observation-only; action rollout and provider flags are unchanged. `GPP_US_SEMANTIC_RESOLVER_PENDING` remains deferred.

Regression entry points: `measurement-consistency.test.ts` (CMP-MEASURE-01 through 10 and Morphe serialization), `v2-session.production.test.ts` (routed head-ping capture), and `audit-runner.production.test.ts` (both-context finalization and debug projection).

## Decision hardening invariants

All persisted correlated findings are resolved in replay before final persistence and then checked by `consistency.ts`. A negative requires explicit `true` completeness for every required capture channel; missing or incomplete state maps to `null`/`inconclusive`, never an absence. CMP provider identity remains available when behavioral verification is inconclusive. Product negatives require applicable commerce context plus complete candidate-local observation, while server-side `not_detected` requires completed passive request capture. Debug exports derive their decision summaries from this same resolved record.

## Important models and APIs

Persisted result fields and UI/API contracts are defined by `StorefrontAudit`. Evidence is persisted as JSONB through `src/db.ts`. Replay is exposed through `POST /api/v1/scans/:id/replay`, `POST /api/v1/replay`, and `scripts/replay.ts`; those consumers must agree.

## Common modification points

- New/changed GA4 or Meta wire shape: update the one central parser, normalized evidence, sanitized fixture, and parser/replay tests.
- CMP signature or precedence: `detect-cmp.ts`; interaction verification belongs in `consent-state.ts`, not detection.
- Product completeness/status: parser facts plus `resolveProductPayloadStatus`; keep PDP URL matching explicit.
- First-party/server-side conclusions: `classify-collection.ts`; actual parsed collection is required.
- New persisted status/field: update `src/types.ts`, replay/resolver/consistency, database columns, API/UI consumers, tests, and versioning.

## Validation

Add or update the smallest sanitized fixture, run its name-filtered test, then:

```text
npm run test:regression
npm run replay -- <fixture-or-evidence>
npm run typecheck
```

Use `npm run validate` for shared contract or cross-domain changes. When detector/resolver behavior changes intentionally, assess whether `RULE_PACK_VERSION` in `src/scanner/version.ts` must be updated.

## Pitfalls and invariants

- Production rules must be generic; never add a domain allow/deny special case to make one fixture pass.
- A GTM container alone and a generic `/collect` endpoint are not GA4 evidence.
- Meta collection seen in any phase cannot later be summarized as absent.
- First-party script hosting is not first-party collection; collector traffic must be parsed.
- Mixed collection is not a duplicate/misconfiguration by itself; strict duplicates match vendor/event/IDs/page context and available client/session identity within the defined window.
- Generic compatibility signals must not outrank provider-specific CMP evidence.
- Access failures dominate negative findings. Prefer an honest inconclusive result to a precise-looking unsupported label.
- Never retain raw secrets, cookie values, authorization headers, or unbounded URLs/base64 outside the established bounded evidence rules.
