## P0 changes and bounds

- Production startup now requires an internal API token, Browserless token, valid USA/EU/UK proxy URLs, and durable storage. It rejects local-browser and memory modes. The checked-in challenge-solving default is off; BrowserQL and GPC side sessions are rejected in production until they share the request guard.
- The scanner rejects non-web schemes, internal hostnames and private literal IPs. Ordinary browser requests are checked against bounded public DNS answers. A blocked request marks network observation incomplete, preventing a negative finding from that incomplete capture.
- Legacy Product Accept and clean-context Accept now require an explicit action cohort, eligible build, verified geo, and eligible provider. Production action eligibility is limited to Cookiebot. Consent V2 Reject also requires verified geo.
- A Consent audit probes actual egress country even in normal mode. Unverified or mismatched egress returns an inconclusive Consent result.
- The public health response exposes counts and build provenance without cooled-down audit domains. Bulk debug ZIP limits heavy audit-detail reads to 25 per request.
- Audit concurrency defaults to 3 and is capped at 10. Bulk submission is capped at 5,000 domains and 10 MB CSV. Lists default to 25 rows, cap at 100, and fetch summary columns only. Detail evidence is fetched for a selected audit. CSV export uses selected fields, caps at 5,000 rows, and escapes spreadsheet formula prefixes. Browser/session cleanup and bounded retry/finalization paths remain in the runner.

## Browser network path and egress control inventory

The default production connection is `scanner Node API/server -> Browserless Cloud WebSocket/CDP endpoint -> remote Chromium -> Browserless internal proxy tunnel -> Decodo external proxy -> destination`. The runner obtains the geo-specific Decodo URL, sets it as the Browserless `externalProxyServer` connection query parameter, and calls `chromium.connectOverCDP`. The current connection builder does **not** use Chrome `--proxy-server`; its Chrome launch arguments are language and window size only. Browserless documents that `externalProxyServer` chains its internal tunnel to the supplied upstream proxy. A single-scan failure can also select the existing Browserless-managed residential fallback (`proxy=residential`, `proxyCountry`); this route is separate from Decodo and must be covered by the egress confirmation. See `src/scanner/audit-runner.ts`, `src/scanner/proxy/decodo.ts`, and `src/scanner/proxy/provider.ts`.

| Layer | Control and what it blocks | Enforcement point | Evidence/source | Can application code bypass it? | Role |
| --- | --- | --- | --- | --- | --- |

| Scanner DNS guard | Rejects a host when its scanner-side DNS answers include private/nonpublic addresses or lookup fails | Node process, before continuing an intercepted browser request | `src/scanner/url-safety.ts`, `src/scanner/audit-runner.ts` | Yes: remote Chromium/proxy can resolve differently or later; Service Worker requests are not all routable | Defense in depth |
| Playwright/browser routing | Aborts unsafe ordinary requests after URL/DNS checks | `browserContext.route('**/*')` in the scanner context | `src/scanner/audit-runner.ts`; [Playwright BrowserContext routing](https://playwright.dev/docs/api/class-browsercontext) | Yes: Playwright says Service Worker-handled requests are not intercepted; routing is not a complete network egress rule | Defense in depth |
| Browserless | Documented Docker built-in URL blocklist prevents navigation to localhost, private IPs, and cloud metadata endpoints; Cloud CDP plus `externalProxyServer` coverage and full address/redirect semantics are **unverified** | Browserless-hosted browser or its internal proxy tunnel, if vendor confirms it applies to these sessions | [Browserless Docker configuration](https://docs.browserless.io/enterprise/docker/config); [Browserless external proxy routing](https://docs.browserless.io/rest-apis/proxies) | A proven, mandatory vendor egress rule would not be bypassable by this scanner's routing code; current Cloud guarantee is unknown | Candidate authoritative boundary; not yet credited |
| Decodo | Geo proxying and a vendor list of restricted website categories; no reviewed Decodo documentation establishes denial of private, loopback, link-local, metadata, IPv6 equivalents, or redirect/resolved-hostname cases | Decodo upstream proxy | [Decodo restricted targets](https://help.decodo.com/docs/dedicated-isp-proxy-restricted-targets); configured proxy URLs in `src/scanner/proxy/decodo.ts` | Unknown for any vendor-side deny rule; this repository can select the Browserless-managed fallback instead | Proxy hop; not credited as authoritative private-egress boundary |
| Production hosting perimeter | Required internal API token; TLS and Cloudflare Access are deployment instructions, not verified here | API ingress at server/platform | `src/production-config.ts`; `docs/ai/domains/deployment-and-configuration.md` | Code cannot bypass a correctly enforced external ingress perimeter, but it does not constrain remote browser egress | Ingress control, not an SSRF egress boundary |

The [Browserless Docker configuration reference](https://docs.browserless.io/enterprise/docker/config) explicitly describes `DISABLE_BLOCKLIST=false` as the default for its Docker deployments. It does not establish that Browserless Cloud BaaS/CDP sessions using `externalProxyServer` inherit the same enforcement, or specify all IPv6, DNS rebinding, redirect, and Service Worker cases. The [Browserless proxy documentation](https://docs.browserless.io/rest-apis/proxies) confirms an internal tunnel and upstream chaining, but makes no private-address security guarantee for that chain. Decodo's documented restricted website categories are not a private-network deny policy. Playwright routing alone is insufficient.

### Required external verification: `BROWSERLESS_PRIVATE_EGRESS_CONFIRMED`

Record an authoritative Browserless documentation/support answer tied to the production Cloud account, endpoint/route, CDP sessions, `externalProxyServer` + Decodo path, and Browserless-managed residential fallback. It must confirm that the browser/network egress boundary denies loopback, RFC1918/private, link-local, cloud metadata, equivalent IPv6 destinations, and resolved hostnames/redirects, including Service Worker-initiated traffic, regardless of the scanner's Playwright handlers. Confirm where the check runs (before forwarding through the external upstream or at another non-bypassable egress point), whether any session flags disable it, and the production setting/plan needed. Save the vendor answer and deployment verification evidence outside this repository's secrets. No new runtime environment variable is needed for this human deployment gate.

If Browserless confirms this for both production routes, mark `P0-1 = closed by infrastructure boundary`, identify Browserless as the authoritative egress boundary, retain the application URL/DNS/routing checks as defense in depth, and set `deployment_readiness = P0_READY` after verifying the setting on the actual deployment. If the guarantee covers only the managed proxy, plan the smallest migration from Browserless -> Decodo to Browserless managed residential proxy: make the existing `browserless_residential` plan the production default; stop requiring Decodo URLs in production startup validation; adapt Decodo-specific retry/telemetry branches to the selected provider; preserve requested USA/EU/UK country targeting and the existing independent egress-country verification. This is a small-to-moderate code/config change with proxy cost, IP pool/stickiness, and site-access differences; scanner findings and Consent action gates must keep their semantics. Do not perform that migration without a vendor answer and a separate change review. If Browserless Cloud provides no suitable boundary, prefer (1) a controlled Browserless deployment with its built-in private-address blocklist and verified egress enforcement, (2) a filtering forward proxy that validates each resolved destination and chains public traffic to Decodo, then (3) another genuine network-level egress control. Infrastructure implementation is outside this package.

### Service Workers

Classification for the main tracking scan: `accuracy_regression`. The main context explicitly allows Service Workers and labels their requests as `service_worker` tracking evidence; blocking them would remove that observation channel by construction. Some isolated fresh Consent/GPC contexts already use `serviceWorkers: 'block'`, but that narrower choice does not prove it is safe for the main audit. Do not change the main context without a deterministic accuracy comparison. Network egress security must not depend on the Service Worker flag.

## Runbook

1. Configure production secrets through the platform secret store: `DATABASE_URL` or `DB_HOST`/`DB_NAME`/`DB_USER`/`DB_PASSWORD`, `INTERNAL_API_TOKEN`, `BROWSERLESS_TOKEN`, and valid `DECODO_PROXY_USA`, `DECODO_PROXY_EU`, `DECODO_PROXY_UK`. Set `NODE_ENV=production`, `USE_MEMORY_DB=false`, `BROWSERLESS_CHALLENGE_SOLVING_ENABLED=false`, and `GPC_EXPERIMENT_ENABLED=false`.
2. Keep `CONSENT_V2_ACTIONS_ENABLED=false`, `CONSENT_V2_ACTION_SAMPLE_PERCENT=0`, and all provider action flags false for observation-only launch. Do not enable an action solely to increase coverage.
3. Close `BROWSERLESS_PRIVATE_EGRESS_CONFIRMED` with the exact Cloud CDP/external-proxy and managed-fallback evidence above, or implement and verify one of the conditional network architectures before accepting arbitrary domains. Put the API behind TLS and the intended access perimeter.
4. On a clean committed checkout run `npm ci`, `npm run build`, then `node dist/server.cjs`. Check `GET /api/health` for `compiled_bundle`, the expected commit, `build_dirty=false`, and `certification_eligible=true`. Run a small non-action canary after deployment.

Offline validation cannot establish live Browserless, Decodo, storefront, or PostgreSQL behavior. Provider certification remains outside this package.
